LibraFlow started as a "just a blog CMS" weekend project and turned into a
publishing platform with paid subscriptions, live reader-author chat, and a
revenue dashboard. This is the build log — what I shipped, where it broke, and
what the growth actually looked like.

## The shape of the thing

Three subsystems, each of which wanted to be its own product:

- A Markdown-aware **editor** with embeds, code blocks, and image uploads.
- A **monetization** pipeline: tips, subscriptions, and soft paywalls via Razorpay.
- A **live layer**: reader-author chat and presence over Socket.io.

<Callout type="note" title="Scope creep, logged honestly">
Every one of these started as "should be a day". The monetization pipeline alone
took three weeks once webhooks, idempotency, and refunds entered the picture.
Budget accordingly.
</Callout>

## The wall: live chat didn't scale the obvious way

The first chat implementation held everything in memory on a single Node process:
a map of room → connected sockets. It was great in development and fell over the
first time two app instances ran behind a load balancer — a message published on
instance A never reached subscribers pinned to instance B.

The fix was a Redis pub/sub backplane so any instance can broadcast to any room:

```js title="chat/gateway.js" {4,11-14}
import { Server } from 'socket.io'
import { createAdapter } from '@socket.io/redis-adapter'

const io = new Server(httpServer)
io.adapter(createAdapter(pubClient, subClient)) // <- the whole fix

io.on('connection', (socket) => {
  socket.on('room:join', (roomId) => socket.join(roomId))

  socket.on('message', async (msg) => {
    // Persist first, then fan out — so history survives a crash.
    await db.messages.insert(msg)
    io.to(msg.roomId).emit('message', msg)
  })
})

```

One line — `io.adapter(...)` — turned a single-process toy into something that
survives horizontal scaling. The lesson filed under "should have known": design
for more than one instance from commit one.

## What I'd do differently

Three things, in order of how much time they'd have saved:

1. **Ship the Redis adapter from day one.** The rewrite was cheap; the debugging that led to it was not.
2. **Treat webhooks as the source of truth for payments,** not the client callback. Clients lie, drop, and retry; the webhook is what actually happened.[^1]
3. **Instrument revenue before growth,** so I could see *which* change moved MRR instead of guessing.

<Callout type="tip" title="The meta-lesson">
The interesting engineering was never the feature — it was the second instance,
the retried webhook, the reconnecting socket. Build for the unhappy path early
and the happy path takes care of itself.
</Callout>

LibraFlow is live at [libraflow.cc](https://libraflow.cc). If you're building
something in this space, the Razorpay webhooks guide[^1] and the Socket.io
scaling docs are the two references I'd start with.

[^1]: Razorpay, *Webhooks & Payment Verification*, razorpay.com/docs — verify signatures server-side and treat the webhook as authoritative.
